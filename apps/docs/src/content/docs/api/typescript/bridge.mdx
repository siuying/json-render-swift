`packages/swift/src/bridge.ts` builds `globalThis.JSONRenderBridge`, an object of plain functions over the catalogs (SwiftUI forms, PDF documents, and any an app adds), core's prompt builders, the spec validator and core's stream compiler. The shipped `json-render-bridge.js` is bundled from `src/bridge-entry.ts`, which calls [`installBridge()`](#installbridge) with the built-in catalogs. The Swift [`JSONRenderBridge`](/json-render-swift/api/swift/json-render-bridge/) actor calls it through `invoke`; you can also call it directly from any JavaScript host.

## Conventions

- **Object arguments may be JSON strings.** Every argument that takes an object (options, a spec, prompt input) also accepts the same value as a JSON string, which is parsed first. For the optional `options` and `initial` arguments, `null` and `undefined` mean "not given".
- **`compilerPush`'s chunk is raw text.** It is never parsed as JSON.
- **Return values are plain JSON.** Results are JSON-serialisable values with no `undefined` members, detached from any internal object (specs are deep-copied through `JSON.stringify`).
- **No host globals.** The bundle runs in a bare `JSContext`: it doesn't need `fetch`, `structuredClone`, `TextEncoder` or `setTimeout`, and `console` is optional.

## Methods

```ts
type CatalogName = "swiftui" | "pdf" | (string & {});

interface CatalogOptions {
  catalog?: CatalogName;
}

interface SystemPromptOptions extends CatalogOptions {
  customRules?: string[];
  mode?: "standalone" | "inline";
}

interface JSONRenderBridgeAPI {
  version(): string;
  systemPrompt(options?: SystemPromptOptions | string | null): string;
  buildUserPrompt(input: {
    prompt: string;
    currentSpec?: Spec | null;
    state?: Record<string, unknown> | null;
    maxPromptLength?: number;
  } | string): string;
  catalogManifest(options?: CatalogOptions | string | null): { components: string[]; actions: string[] };
  jsonSchema(options?: ({ strict?: boolean } & CatalogOptions) | string | null): object;
  validateSpec(spec: unknown, options?: (CatalogOptions & ValidateSpecOptions) | string | null): SwiftUISpecValidation;
  autoFixSpec(spec: Spec | string, options?: CatalogOptions | string | null): Spec;
  createCompiler(initial?: Spec | string | null): number;
  compilerPush(handle: number, chunk: string): { spec: Spec; newPatches: JsonPatch[] };
  compilerFinish(handle: number): Spec;
  compilerDispose(handle: number): void;
  invoke(method: string, argsJSON?: string | null): string;
}
```

`@json-render/swift/bridge` exports this shape as the type `JSONRenderBridgeAPI`, plus `Catalog`, `CatalogName`, `BuiltInCatalogName`, `CatalogOptions`, `InstallBridgeOptions`, `SystemPromptOptions` and `UserPromptInput`. `ValidateSpecOptions` and `SwiftUISpecValidation` come from [`@json-render/swift`](/json-render-swift/api/typescript/swift/#validatespecforcatalog).

### Catalog selection

`systemPrompt`, `catalogManifest`, `jsonSchema`, `validateSpec` and `autoFixSpec` read a `catalog` option:

| `catalog` | Catalog |
|---|---|
| missing, `undefined` or `null` options | `"swiftui"` |
| `"swiftui"` | The forms [`catalog`](/json-render-swift/api/typescript/swift/#catalog). |
| `"pdf"` | [`pdfCatalog`](/json-render-swift/api/typescript/swift/#pdfcatalog). |
| a name passed to `installBridge({ catalogs })` | That catalog. |
| anything else | Throws `Error("Unknown catalog: <name> (expected swiftui \| pdf)")`. The list names every catalog the bridge has, custom ones after the built-ins. |

`buildUserPrompt` and the compiler methods take no catalog: the user prompt and JSON patch compiling are the same for every catalog.

| Method | Description |
|---|---|
| `version()` | The `@json-render/swift` version the bundle was built from, for example `"0.1.0"`. `"0.0.0-dev"` when `src/bridge.ts` runs from source. |
| `systemPrompt(options?)` | The selected catalog's `prompt()`, with only `customRules` and `mode` passed through. |
| `buildUserPrompt(input)` | Core's `buildUserPrompt` with `prompt`, `currentSpec`, `state` and `maxPromptLength`. A non-empty `currentSpec` makes it an edit prompt; a non-empty `state` is appended as `AVAILABLE STATE`. |
| `catalogManifest(options?)` | Copies of the selected catalog's `componentNames` and `actionNames`. The PDF catalog's `actions` is `[]`. |
| `jsonSchema(options?)` | The selected catalog's `jsonSchema()`. `{ strict: true }` throws instead: strict structured-output schemas can't express the `elements` and `state` maps, whose keys the model chooses, so the result would only allow an empty `elements`. Generate with the system prompt and the patch stream. |
| `validateSpec(spec, options?)` | [`validateSpecForCatalog`](/json-render-swift/api/typescript/swift/#validatespecforcatalog)`(selected, spec, { hostValidators, hostActions })`. `hostValidators` and `hostActions` are passed on only when they are arrays. Never throws for an invalid spec. |
| `autoFixSpec(spec, options?)` | [`autoFixSpecForCatalog`](/json-render-swift/api/typescript/swift/#autofixspecforcatalog)`(selected, spec)`. |
| `createCompiler(initial?)` | Creates a core `createSpecStreamCompiler` seeded with a copy of `initial`, or with `{ "root": "", "elements": {} }`, and returns its handle. Handles are integers counting up from 1, unique per bridge object. |
| `compilerPush(handle, chunk)` | Pushes stream text. Returns the spec so far and the patches this chunk applied. |
| `compilerFinish(handle)` | Applies a buffered final line without a trailing newline, returns the final spec and frees the handle. |
| `compilerDispose(handle)` | Frees the handle without flushing. Does nothing for unknown handles and returns `undefined`. |
| `invoke(method, argsJSON?)` | Calls any other method for string-only callers. See below. |

`compilerPush` and `compilerFinish` throw `Error("Unknown compiler handle: <handle>")` for a handle that was never created, or was already finished or disposed. Compilers live in a `Map` inside the bridge object until finished or disposed, so free every handle you create.

## installBridge

```ts
import { installBridge } from "@json-render/swift/bridge";
import type { Catalog, InstallBridgeOptions } from "@json-render/swift/bridge";

type Catalog = CoreCatalog<any, any>; // what defineCatalog returns

interface InstallBridgeOptions {
  catalogs?: Record<string, Catalog>;
}

function installBridge(options?: InstallBridgeOptions): JSONRenderBridgeAPI;
```

`installBridge` builds a bridge over the built-in catalogs (`swiftui`, `pdf`) followed by `options.catalogs`, assigns it to `globalThis.JSONRenderBridge` (replacing any bridge already there) and returns it. Each call makes a new object with its own compiler handles. It throws, and installs nothing, when:

- a custom name is built in: `Catalog name "pdf" is built in and cannot be replaced; choose another name (built-in catalogs: swiftui, pdf)`,
- a value isn't a catalog (no `prompt`, `validate`, `jsonSchema`, `componentNames` or `actionNames`): `Catalog "<name>" is not a catalog; create it with defineCatalog from @json-render/core`.

Importing `@json-render/swift/bridge` has no side effects. An app with its own catalogs writes an entry that calls `installBridge`, bundles it like [the shipped bundle](#bundle) and loads it in Swift with `JSONRenderBridge(script:sourceURL:)`:

```ts title="bridge-entry.ts"
import { installBridge } from "@json-render/swift/bridge";
import { databaseCatalog } from "./database-catalog";

installBridge({ catalogs: { database: databaseCatalog } });
```

Every catalog-aware method works for a custom catalog whose spec is an element map (`{ root, elements, state? }`, as core's `defineSchema` builds it): `validateSpec` and `autoFixSpec` read which element fields (`on`, `watch`, `repeat`, `slots`) its schema declares. [Extending the catalog](/json-render-swift/guides/extending-the-catalog/#add-a-catalog-in-your-app) has the esbuild settings and the Swift side.

## invoke

```ts
invoke(method: string, argsJSON?: string | null): string
```

`invoke` wraps the other methods for callers that can only pass and receive strings:

- `argsJSON` is a JSON array of arguments. A missing or empty `argsJSON` means no arguments. A JSON value that isn't an array is passed as the single argument.
- It returns a JSON string, `{"result": <value>}` on success. An `undefined` result (from `compilerDispose`) is sent as `null`.
- On any error it returns `{"error": {"message": "...", "stack": "..."}}` instead of throwing. `stack` is omitted when the error has none.
- An unknown method name, or `"invoke"` itself, returns the error `Unknown bridge method: <method>`. Invalid `argsJSON` returns the `JSON.parse` error.

```js
bridge.invoke("version");
// '{"result":"0.1.0"}'

bridge.invoke("validateSpec", JSON.stringify([spec]));
// '{"result":{"valid":true,"issues":[]}}'

bridge.invoke("catalogManifest", JSON.stringify([{ catalog: "pdf" }]));
// '{"result":{"components":["Document","Page","View",...,"PageNumber"],"actions":[]}}'

bridge.invoke("catalogManifest", JSON.stringify([{ catalog: "html" }]));
// '{"error":{"message":"Unknown catalog: html (expected swiftui | pdf)","stack":"..."}}'

bridge.invoke("compilerPush", JSON.stringify([handle, '{"op":"add","path":"/root","value":"x"}\n']));
// '{"result":{"spec":{"root":"x","elements":{}},"newPatches":[{"op":"add","path":"/root","value":"x"}]}}'

bridge.invoke("compilerDispose", "[987654]");
// '{"result":null}'

bridge.invoke("nope");
// '{"error":{"message":"Unknown bridge method: nope","stack":"Error: Unknown bridge method: nope\n    at ..."}}'
```

The Swift actor calls only `invoke`, and always passes the `catalog` option for catalog methods. It applies `hostActions` itself after `validateSpec` returns and never sends `hostValidators`. It serializes the arguments with `JSONValue.jsonString()`, so object arguments arrive as already-parsed JSON values inside the array, and decodes the envelope: `result` becomes the Swift return value, and `error` becomes `JSONRenderBridgeError.javaScript(message:stack:)`. An exception that escapes `invoke` (only possible with a custom script) is read from `JSContext.exception` and thrown the same way.

## Calling the bundle directly

### From JavaScriptCore

```swift title="RawBridge.swift"
import Foundation
import JavaScriptCore

let url = Bundle.main.url(forResource: "json-render-bridge", withExtension: "js")!
let context = JSContext()!
context.evaluateScript(try String(contentsOf: url, encoding: .utf8), withSourceURL: url)
let bridge = context.objectForKeyedSubscript("JSONRenderBridge")!

// Direct call: object arguments may be JSON strings.
let prompt = bridge.invokeMethod("systemPrompt", withArguments: [#"{"mode":"inline"}"#])!.toString()!

// String-only call: a JSON array of arguments in, a JSON envelope out.
let envelope = bridge.invokeMethod("invoke", withArguments: ["catalogManifest", "[]"])!.toString()!
// {"result":{"components":["Form","Section",...],"actions":["submit",...]}}
let pdf = bridge.invokeMethod("invoke", withArguments: ["catalogManifest", #"[{"catalog":"pdf"}]"#])!.toString()!
// {"result":{"components":["Document","Page",...],"actions":[]}}
```

This assumes you copied `json-render-bridge.js` into your app bundle. In most apps, use the Swift [`JSONRenderBridge`](/json-render-swift/api/swift/json-render-bridge/) actor instead: it loads the copy inside the package, keeps the context on one actor and turns errors into Swift errors. A `JSContext` must not be used from two threads at once.

### From Node

```js title="bridge-in-node.mjs"
// Run from the repository root after `pnpm build`.
import { readFileSync } from "node:fs";
import vm from "node:vm";

const source = readFileSync("packages/swift/dist/json-render-bridge.js", "utf8");
const context = vm.createContext({}); // bare global: no console, fetch, timers...
vm.runInContext(source, context, { filename: "json-render-bridge.js" });
const bridge = context.JSONRenderBridge;

bridge.version(); // "0.1.0"

const handle = bridge.createCompiler();
bridge.compilerPush(handle, '{"op":"add","path":"/root","value":"form"}\n');
const spec = bridge.compilerFinish(handle); // { root: "form", elements: {} }
```

Values returned from the `vm` context belong to another realm, so `instanceof Array` checks against them fail. Copy them with `JSON.parse(JSON.stringify(value))` when that matters. In Node you can also import `@json-render/swift` directly; see [Usage in Node](/json-render-swift/api/typescript/swift/#usage-in-node).

## Bundle

`pnpm build:bridge` (also the second step of `pnpm build`) runs `scripts/build-bridge.mjs`, which bundles `src/bridge-entry.ts` with esbuild:

| Setting | Value |
|---|---|
| Format | IIFE that calls `installBridge()`, which assigns `globalThis.JSONRenderBridge` |
| Platform | `neutral`, with `mainFields: ["module", "main"]` |
| Target | `safari18` |
| Minify | On; pass `--no-minify` for readable output |
| Defines | `process.env.NODE_ENV` = `"production"`, `__BRIDGE_VERSION__` = the package version |
| Bundled | `@json-render/core`, both catalogs (forms and PDF) and `zod`: about 271 KB minified |
| Zod locales | A plugin replaces zod's locale index with English only, which drops about 250 KB of messages |
| Banner | A comment naming the package and core versions, then a `console` stub with no-op `log`, `info`, `warn`, `error` and `debug` when `globalThis.console` is undefined |

The script writes `packages/swift/dist/json-render-bridge.js`, copies it to `swift/JSONRender/Sources/JSONRenderSwiftUI/Resources/json-render-bridge.js`, and prints the bundle size broken down by package. With the same settings it bundles `test/fixtures/test-catalog-bridge.ts`, a bridge with an extra `"test"` catalog, into `fixtures/bridge/test-catalog-bridge.js` for the Swift tests.

tsup also builds `src/bridge.ts` as the `@json-render/swift/bridge` entry point, with `__BRIDGE_VERSION__` defined, so an app bundle's `version()` reports the package version.

<Aside type="caution">
The copy in the Swift package and the test fixture are checked in and must not be edited by hand. `pnpm test` first runs `pnpm check:bridge` (`build-bridge.mjs --check`), which builds both into a temporary directory and fails when either checked-in file differs, without writing anything. Rebuild with `pnpm build:bridge` after every catalog, prompt or dependency change.
</Aside>

### Testing in a bare context

`test/bridge.test.ts` evaluates the built bundle in `vm.createContext({})`, a context with no host globals, and checks that `fetch`, `structuredClone`, `TextEncoder`, `setTimeout` and `process` are all undefined there. It then exercises every method in that context: `version()` against `package.json`, `systemPrompt()` against `catalog.prompt()` with object and JSON-string options, edit and fresh user prompts, the manifest and JSON Schema (and the `strict: true` rejection), validation with `hostValidators` and `hostActions`, auto-fix, the `catalog: "pdf"` option on every catalog method, chunked compiling of `fixtures/specs/registration.jsonl` (which must reproduce `registration.json`), independent handles, disposal, and the `invoke` envelopes, including unknown methods and invalid `argsJSON`. It also checks that the shipped bundle has only the built-in catalogs, and tests `installBridge` from source: that importing it installs nothing, that a custom catalog is selected by every catalog method, that each bridge keeps its own compiler handles, the built-in name and non-catalog errors, and the list of names in `Unknown catalog`. Two regressions cover custom catalogs in the validator: a `FieldSet` component outside the PDF catalog gets no form-field checks, and a schema that declares `watch` but not `on` still has its `watch` bindings checked. Finally it loads `fixtures/bridge/test-catalog-bridge.js` in another bare context. Run `pnpm build` before `pnpm test`; the suite fails early when the bundle is missing.
